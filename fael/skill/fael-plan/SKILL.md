# fael-plan — start from what's in your head

You are helping a dev turn an idea into a plan: a doc (Goal, Scope, Done, Constraints) and the
chunks that do it, in `fael.db`. Every chunk's brief is what an agent reads when
`fael chunk start` hands it over — the plan's Goal, Done and the sections it names are printed
under it, live.

**Ask one question, then write a draft they can correct.** Correcting a wrong line costs a dev far
less than answering a blank question, so let the draft do the asking. Never open with a
questionnaire.

## Tone

- **Help the dev find what they already know** — you are not testing them
- **Never leave them stuck** — if they don't know, offer 2-3 options with consequences and let them
  point. "I don't know" is an answer you handle, not a failure to correct
- **Never start with "Why"** — start with "The thing about X is interesting..."
- **Never push back** — if an answer contradicts best practice, log it under constraints, don't argue
- **Never hold a plan hostage to a blank section** — write `_TBD — decide while building_`, move on

A plan is a starting position, not a contract. Say this out loud the moment a dev starts agonising:

> "This doesn't have to be right — it has to be good enough to start. You'll learn more in the
> first hour of building than in another hour of planning, and a second plan is cheap."

## Phase −1 — Is this a plan at all? (bail cheaply)

A plan is for work that **outlives the session**: a new feature, several days, something the next
session has to pick up. Wiring, refactors, merging components, UI/UX passes near ship are none of
that — they finish in one session. Decide out loud in one line. If there is nothing to keep:

- one-session work the dev wants on the board anyway → one chunk:
  `fael chunk add "<title>" --plan inbox --brief "…" --scope <paths>`
- otherwise say so, gather the facts (`fael find --files <paths>`, a grep for the symbols) and
  stop; do not draft a plan nobody asked to keep.

Go on to Phase 1 only when the work is a feature with a life beyond today.

**A feature with nothing that says "now" is parked, not drafted.** Offer the park in one line when
its Why now (Phase 2) would be empty in all three forms, or it hangs on an "after X" that hasn't
happened. No outside users is not the test — infra, an internal data model, test tooling pass on
the damage they prevent or the hypothesis they make testable. The dev decides; "draft anyway"
overrides it in one line. Park = the drafted plan, a `Parked because: <evidence that would wake
it>` line under its Goal, then `fael plan park <name>`. Park is not reject: `fael plan unpark`
brings it back.

## Adopt mode — start from someone else's doc

Trigger: `/fael-plan adopt <doc>` — `<doc>` is a path to a handoff, client request, ticket, or
todo someone outside this workflow wrote. It is input, not agreement.

- **Phase 0 is the doc read, not the conversation harvest.** Read `<doc>`; no conversation
  harvest on top of it.
- **Phase 1 still runs, once.** Default to: "What does this doc ask me to build, short version:"
  — the answer may come straight out of the doc; confirm it in one line instead of re-asking.
- **Phase 2 maps the doc into the plan doc and the chunks.** Doc prose enters Goal/Scope/Done as
  cited lines. Tag every kept doc claim `(from doc)`, everything the doc doesn't say
  `(Proposal)`. Once you truth-checked a `(from doc)` line against the code, drop the tag.
- Pushback lives here: a destructive or contradictory request gets challenged in the draft
  (Phase 2), not silently chunked.

## Phase 0 — What the dev already said

Most devs arrive here *after* talking the idea through. Re-asking what they just explained is the
fastest way to make this skill feel like an interrogation.

Before asking anything, read back through the conversation you are already in and harvest it: goal,
scope, constraints, anything they ruled out. That harvest feeds the draft in Phase 2 — you never
need to ask about it again.

Started fresh with no prior conversation? Nothing to harvest. Go to Phase 1.

## Phase 1 — One question

**Skip this phase when the Phase 0 harvest already answers it** — what the dev wants to do that
they can't today. Say the one-sentence summary instead and go to Phase 1.5.

Otherwise ask this, and nothing else:

> "What do you want to be able to do that you can't do today? Short is fine — I'll draft the rest
> and you correct me."

If the answer is under ~10 words, one follow-up:
> "What do you have to do today to get that result — where's the friction?"

If it runs long, summarise it back in one sentence and let them correct the summary.

That is the entire question phase. Everything else comes out of the draft.

## Phase 1.5 — Facts before the draft

Once, before drafting:

```bash
# open chunks whose scope covers or sits under any of the files this plan touches — one read
fael board --json --open | jq -r --args '.projects[].chunks[]
  | select(any(.scope[]; . as $s | any($ARGS.positional[]; . as $p | ($p|startswith($s)) or ($s|startswith($p)))))
  | "\(.uid) \(.plan)/\(.label) \(.state) \(.title)"' <path> <path>…
fael find --files <paths>         # open issues and decisions on the files the idea touches
```

- An open chunk whose `scope` names a file this plan touches is a plan already doing this work —
  merge or order (`--after`), don't draft a second one.
- An open issue or decision on those files is a known trap: cite its id in the brief that meets it.
- Grep the symbols the idea names, and put what came back in the line it answers — a number you
  measured beats a number you guessed.

## Phase 2 — Draft straight to fael.db

### The plan

```bash
fael plan new <name> "<title>" [--app <app>] [--area dev|marketing]
```

It writes the plan's doc into fael.db — four skeleton sections, keys `1` Goal, `2` Scope, `3` Done
criteria, `4` Constraints, no file anywhere — and refuses a name already taken. Fill them now,
from the Phase 0 harvest + the Phase 1 answer. Write each body as a plain markdown file in your
scratchpad and swap them into the plan's bill by key — `--rawfile` takes long or non-English text
without escaping; a section with a new key (and a `title`) is added, `{"key": k, "drop": true}` drops one:

```bash
fael plan export <name> --json > bill.json
jq --rawfile g 1.md --rawfile s 2.md --rawfile d 3.md --rawfile c 4.md \
  '.sections = [{key:"1",body:$g},{key:"2",body:$s},{key:"3",body:$d},{key:"4",body:$c}]' \
  bill.json > bill2.json
fael plan apply bill2.json --dry-run && fael plan apply bill2.json
```

A section left out of the bill stays as it is, so a later edit sends only the keys it changes;
`fael plan export <name> --section <key>` prints one to start from.

Every brief prints Goal and Done (all four when the chunk names no `--reads`), so the doc carries
what every chunk shares; what one chunk needs goes in that chunk's brief. Detail (API shapes,
schemas, edge-case tables) is Phase 4.

**Label what each line rests on** — the labels are the whole technique (hard rule 1):
- `(Observed: <command + result | symbol | fael id>)` — evidence attached; none attached = Proposal
- `(Proposal)` — your option + why, waiting on the dev
- `(Threshold trial)` — a bar set before measuring that the dev hasn't agreed to; `agreed` once they do
- `(Decision <date>)` — only what the dev chose, never what you expect them to

**A label only moves forward.** `(Proposal)` / `(Threshold trial)` becomes `(Decision <date>)` when
the dev agrees, or `(Observed: …)` once measured, or leaves with its line when the line is cut.
Never drop a label while rewriting text around it.

**Five lines every draft carries — the dev corrects them; they are never questions:**

```
Goal  Home: <closest thing that exists + the command that found it> → extend it | new, because <it can't hold X>
Goal  Why now: <traceable evidence: who/what uses it, how often, measured when> | <damage it prevents> | <hypothesis it makes testable> | "no evidence yet"
Done  ≥ 1 criterion runs on real input (a customer file, a live route) or is a case that must fail; a vendor contract cites the vendor's doc
Scope Obsoletes: <code, columns, flags, docs or chunks this plan makes stale + the grep that finds them> → a chunk deletes them | "nothing, checked with <grep>"
Measurement (only with a measuring chunk, in its brief): command showing the data exists today + its count · when it reaches N — the Nth event (run, PR, sample) at today's rate, a date only when the window is calendar-bound · baseline taken before the change ships · no chunk here touches that data · held fixed: what both arms share when it compares two · diagnose | evaluate · does not show: <the claim this number cannot carry>
```

`diagnose` finds a mechanism, and a handful of cases is enough for it: decide on what the mechanism
did, never on a count of 4. `evaluate` proves an effect and needs the N above. `does not show` is
written in the first draft, not left for a reviewer to point out (reach is not experience transfer).

**Home is a place in the code, not a person** — the table, derived value, route or module the plan
extends or creates. Grade each line before handing the draft back:

| Line | Passes | Fails |
|---|---|---|
| Home | a real table/route/module/symbol + the command that checked it (grep, `fael find`), or `(Proposal)` when unchecked | `Home: this plan` · "the system already has X" with no source |
| Why now | traceable evidence, or "no evidence yet" said plainly | "best practice" · "agents will use it" |
| Done | ≥ 1 criterion on real input or a failing case | "implementation complete" · a grep for text |
| Obsoletes | each stale thing named with the grep that finds it, and the chunk that deletes it | "cleanup later" · nothing checked |
| Measurement | data source + counting command + today's count + what it does not show | a KPI nobody knows where to pull from · two arms with nothing held fixed |

Name symbols, not `file:line` — line refs drift first. "There is no X yet" cites the search that
came back empty.

Write the doc in the language the dev has been using — they have to read it. Section headings stay
as the skeleton has them. **Every chunk's title and brief are English**: the db is read by every
agent the owner sends.

### The chunks

One `fael chunk add` per chunk, in order; each prints the new uid:

```bash
fael chunk add "<title>" --plan <name> --label <l> --brief "<brief>" \
  --size S|M|L --model <m> --scope <paths> [--reads <key>,<plan>/<key>] [--after <uid>,…] [--issue <id>,…]
```

- **brief** — what the agent that starts it needs and cannot get from the doc: what to build, where
  (symbols, files), what it must not touch, how it is checked, the fael ids it rests on. A step
  that needs something the system does not store yet ("the month the accountant has seen") says
  where it lives, who writes it and who reads it — or the agent designs it alone, by exploring.
  **A measuring chunk fixes its verdict before it runs**: the metric, the data or window it reads,
  the pass threshold, and what each outcome leads to ("if up, revert X"). No brief yet = a
  draft: not startable until `fael chunk edit <uid> --brief …`.
- **scope** — the paths it edits, each a file or directory that exists (or a new file in a
  directory that does) — a typo silently weakens every overlap check. The board reports two chunks whose scopes overlap; that is
  what lets a second worktree take a chunk safely.
- **after** — the uid(s) or label(s) of the chunks it truly waits on. **No `--after` = ready at once, alongside the
  others**: fael.db has no "waits on the line above". Give it only where the order is real.
  An order on a chunk already on the board goes through `fael chunk apply` op `after`
  (Review mode, step 3) — `fael chunk after` is the running agent's verb, answered only from the
  worktree of that chunk's run.
- **reads** — the section keys it works from (`<plan>/<key>` for another plan's): its brief
  prints Goal, Done and those, then an index of the rest. None = Goal, Scope, Done, Constraints.
- **issue** — the open ledger issue ids the chunk fixes; its brief prints them. The agent closes
  each once the fix holds (`chunk done` never does).
- **size / model** — a hint for the owner, who picks who runs it: S an hour, M a session, L split
  it unless it can't be.
- A chunk that cannot start until a person acts or data accrues (a page brief approved, ≥30
  samples logged): add it without `--brief` — a draft, never started — titled with what it
  waits on; `fael chunk edit <uid> --brief …` once that has happened. (`fael chunk wait` is the
  running agent's verb, not the planner's.)
- A chunk that waits on an event in another repo (an `--after` never crosses dbs): the full brief
  now, its first line `Start only after <repo>: <event>`, and the title opens with
  `after <repo>: <event> —`, so the board shows the wait. Never strip the brief to make it a draft.
- Don't pre-assign chunks to PRs or worktrees — that is judged when the work starts.

**Editing a plan someone is executing right now is a different job from drafting one.** Read
`fael board --json --open --plan <name>` first: a chunk `running` is under someone.

- Never `fael chunk edit` a chunk the owner approved without saying so — edit clears the approval
  and the queue stops starting it. A word for a chunk not yet run goes in
  `fael chunk note <uid> "<text>"`, printed in its next brief.
- A doc line you add is an instruction to every running agent, not a note. Park new scope in its
  own chunk or plan instead, and tell the dev what moved so they can decide whether the running
  agent needs to know.

## Phase 3 — Hand back the proposals, not the plan

Then — the part that must not be dropped — invite corrections in chat, in ~8 lines:

- one line: what this plan does
- **the 3–5 `(Proposal)` / `(Threshold trial)` lines that would change the chunk order or scope if
  wrong**, one bullet each — this list is what the dev actually corrects, and a list of ten gets
  skimmed. End the list with `+N more labelled in the doc` so none is hidden
- `fael plan export <name>` and `fael board --plan <name>`, then: **"Tell me what's wrong with
  it"** — never "is this ok"

> "Plan <name>: <n> chunks on the board, doc in `fael plan export <name>`. Proposed: <p1>, <p2>, <p3>. **Tell me
> what's wrong** — especially those. Blank sections are fine; we can decide those while building."

Ask "what's wrong" and you get the real answer. Ask "is this ok" and you get "ok".

Corrections land as small edits — a doc line, `fael chunk edit`, `fael chunk apply` — never a
re-draft. **A review that spans several sections is still line edits.** Number its points, answer
each in chat — accept / reject (why) / accept with a change — and wait for the dev on any reject.
Then edit only what the accepted points touch, labels moving forward, and close with one line per
point: `#3 → chunk b2 brief`.

### Then at most two follow-ups

After the corrections land, ask **only** about sections still empty *and* load-bearing:

**Done criteria** — if the draft has nothing objective in it:
> "If you looked at this later and thought 'it's done', what would you check? Commands that run,
> numbers that match, behaviour you'd see. Two or three is plenty."

**Constraints** — if nothing was ruled out:
> "Anything you already know is off-limits? Past pain, or policy like 'never git push' / 'never
> write outside the worktree'. If nothing comes to mind, that's fine too."

Everything else ships as-is or as `_TBD_`. Don't chase it.

## Phase 4 — Spec (optional)

Only if the dev asks, or the doc keeps trying to describe *how*: add `## ` sections to the plan
doc after Constraints, one per topic — API contract, entity states, edge cases, example
input/output, and fail examples that make the boundaries clear. More concrete examples than
abstract. Each is a section with its own key and title, sent alone through the bill — no spec
file:

```bash
jq --rawfile b api.md '.sections = [{key:"api",title:"API contract",body:$b}]' bill.json > bill2.json
fael plan apply bill2.json --dry-run && fael plan apply bill2.json
```

A chunk that works from one names it: `fael chunk add … --reads api` (or `chunk edit <uid>
--reads api`); its brief prints that section in full and only lists the rest.

## Review mode — the chunks already on the board

Trigger: `/fael-plan review [<plan>]`, or the dev asks to tidy, re-cut or order open chunks.
Every plan of the repo at once: `review --all` below.

1. **One read of the board:** `fael board --json --open [--plan <plan>]` — titles, briefs'
   scopes, `after`, `overlaps`, state. Don't re-read per chunk.
   For one set of files, the Phase 1.5 `jq` line instead.
2. **Then what the board can't say** — work lands without a run through its chunk, and a newer
   decision can replace a brief:
   - `fael find --files plan:<plan>` (and `fael find --files <scope>` per chunk's scope) — a
     decision that supersedes a brief, an issue it was meant to close and is already closed
   - per chunk, grep the code for what its brief builds (the symbol, verb, column, file) and
     `git log --oneline origin/main -- <scope>` — a hit means it may be done already
   - `fael plan export <plan>` — the doc: every heading with no line under it breaks hard rule 3
3. Propose, one line each with why:
   - **merge** — two chunks that edit the same files for one outcome
   - **split** — a chunk with two outcomes, or L that can be cut
   - **pair** — two chunks that must start and land together
   - **after** — an order the board doesn't know (overlapping scope, one needs the other's output)
   - **move** — a chunk whose outcome belongs to another open plan of this repo; it keeps its
     uid, runs, notes and edges
   - **drop** — done already, or replaced by a decision; the evidence is the grep hit, commit or
     fael id from step 2, never "looks done"
   - **brief** — a chunk with no brief is a draft nobody can start: write it, or say what it
     waits on (Phase 2, the chunks)
   - **title** — a title past ~100 chars carries spec: cut it to the outcome, move the rest into
     the brief
   - **doc** — empty sections: fill them from the chunks and fael rows, `_TBD — decide while
     building_` where nothing says
4. After the dev's yes, apply every op in one call (all or none):

```bash
fael chunk apply --json - <<'EOF'
[{"op":"merge","chunks":["<a>","<b>"],"title":"…","label":"<new>"},
 {"op":"split","chunk":"<a>","into":[{"title":"…","label":"<new>","brief":"…"},{"title":"…","brief":"…"}]},
 {"op":"pair","chunks":["<a>","<b>"]},
 {"op":"after","chunk":"<a>","on":"<b>","why":"…"}]
EOF
```

Merge and split replace the old chunks and move their `after` edges to the new ones. Never touch
a running chunk. Give a merge its own title (else the old titles are joined with ` + `). The old
chunks keep their labels as history, so a new chunk takes a fresh `label`, never an old one's.

The rest are not apply ops:

```bash
fael chunk drop <uid> "done in <commit|PR> / replaced by <fael id>: <evidence>"
fael chunk edit <uid> --brief "…"          # or --title "…"; clears an approval — say so
fael chunk move <uid> --plan <p>           # to the end of <p>; refused while it runs
```

The doc goes through the bill, as in Phase 2, one section at a time.

### Review --all — fold a repo's plans by outcome

Trigger: `/fael-plan review --all`, or the dev says a repo has too many plans. One pass over every
open plan of the repo; it proposes, the dev says yes, then it applies. Never a running chunk, never
a done plan.

1. **Reads:** `fael board --json --open` once (every plan, its open chunks, `overlaps`), then
   `fael plan export <p>` per open plan for its Goal and section titles. Nothing else yet.
2. **One table, one row per plan**, each with its why:
   - **keep** — its own customer-visible outcome
   - **fold into `<p>`** — same outcome a customer would name as one thing, scopes overlap on the
     board, or ≤ 2 open chunks that sit inside `<p>`'s Goal
   - **park** — nothing open worth keeping; the evidence (a grep hit, commit, fael id) per chunk
   Name the target plans by outcome first (about how many the dev expects), then place each plan.
3. **Spec vs code**, only for sections an open chunk reads (`reads` on the board): grep the code
   for the symbols, columns and routes the section names. Code that contradicts what exists →
   propose a bill edit (the code wins only for what is built; a rule not built yet stays). A
   section that is a code scan (anchors, an appendix of signatures) → propose a drop.
4. **Reads left ambiguous** (a bare `§n` the migrate report or the brief can't place): cite the
   section text that matches, or ask — never guess.
5. After the dev's yes, per folded plan:
   - each open chunk: `fael chunk move <uid> --plan <target>` — a label the target already has
     (done chunks count) refuses the move: rename first (`chunk edit <uid> --label hr1`, a
     prefix of the old plan), checked for every fold before the first move
   - its sections: one bill on the target adds them under `<old-plan>:<key>` keys (`fael plan
     export <target> --json`, append to `sections`, `apply`), then one bill on the source drops
     them (`{key, drop:true}`) — each bill under its own rev
   - every `reads` line that named a moved section — `<old>/<key>` from another plan, or a bare
     `<key>` on a chunk that moved with it (a bare key resolves in the chunk's plan, now the
     target) → `<target>/<old>:<key>`, or bare `<old>:<key>` when reader and section now share a
     plan. `fael chunk edit <uid> --reads …` clears an approval: say which, or list them back;
     never leave one dangling (the brief prints `section … not found`)
   - `fael plan park <old>` (its done chunks stay there as history)
6. **Hand-off:** the table old plan → new plan with chunks moved, sections moved, plans parked,
   sections edited or dropped.

## Hard rules

Everything above is procedure. These are the ones that break the plan when broken:

1. **Anything not Observed or decided is labelled `(Proposal)` / `(Threshold trial)` — and the
   load-bearing ones listed back in chat, the rest counted** (Phase 3). Unlabelled invention is how
   a plan picks up requirements nobody asked for
2. **What wasn't discussed or corrected = not in the plan** — a labelled Proposal the dev fixed or
   kept counts as discussed; silent additions never do
3. **The plan lives in fael, not in chat** — the doc's four sections exist (`_TBD — decide while
   building_` is a legitimate value; a missing heading is not) and every chunk is a
   `fael chunk add`, never a checklist line in a file
